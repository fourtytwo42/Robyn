# Live contract and integration due diligence

Last verified: 2026-07-20

## Executive conclusion

The shortest credible route is still an adapter proof followed by a native implementation, but the live-contract audit materially narrows what can be reused:

- **Vladdy is proof and a design reference, not an adapter seam.** Its verified contracts implement a strong single-reward-asset accumulator, but stock mode is mutually exclusive with its other fee destinations, the factory accepts any nonzero “stock” token rather than enforcing Robinhood's canonical registry, and the deployed hook cannot represent a weighted multi-asset basket.
- **Alloy is useful source, not deployable software.** The old verified deployment differs from the documented 70/20/10 economics, the repository does not currently have a reproducible passing test suite, and the published keeper/index address records are invalid or empty.
- **Bags remains the first adapter to test.** Its factory and vault are verified upgradeable proxies and its product exposes multiple creator-fee claimers. A funded compatibility spike must prove a contract can receive, account for and claim the share without an EOA-only or signature assumption.
- **pons is the second adapter to test.** Its creator-selected fee-wallet model is simple, but its fee and redirect path must be exercised with a contract recipient.
- **BASKET, Vimen, OpenZeppelin and Safe are reusable at the pattern/library level.** BASKET's verified factory supplies a useful canonical-token/oracle registry reference. Vimen is the stronger open-source mint/redeem basket reference. Neither replaces Robyn's fee-funded reward controller.

The machine-readable evidence is in [live-contract-audit.json](live-contract-audit.json), generated by [audit-live-contracts.py](../scripts/audit-live-contracts.py). The script is read-only and sends no transactions.

### Vladdy's useful mechanism and its trust boundary

Vladdy deploys a per-launch `StockRewardsDistributor` using magnified cumulative reward-per-share accounting. Token transfers adjust correction balances, so rewards follow the holder who earned them without looping over every wallet. Holders pull rewards with `claim()`. This is the right family of accounting for a native Robyn token.

The conversion path has two very different modes:

1. A configured Uniswap v4 native-ETH/stock route can buy the asset with a caller-supplied `minStockOut` and deposit it into the distributor.
2. A fallback `releaseStockReserve` sends ETH to a trusted agent, after which the agent is expected to buy and deposit the stock.

The second route is custodial at the moment of conversion and creates an agent-performance and solvency assumption. Platform ownership also controls stock routes. Robyn should not describe either design as trustless unless every enabled route is atomic, restricted to canonical output tokens, bounded by expiry/minimum output and independently price-checked.

The source bundle contains project files tagged MIT, but also bundled dependencies tagged MIT, BUSL-1.1 and UNLICENSED. Verified source is not permission to copy. Obtain a repository/license grant or independently implement the observed behavior with properly licensed primitives.

### Alloy provenance correction

The repository at commit `ffbc72de1aa3ea4b354916c06e178250dfb74d27` is MIT-licensed, but it is not currently a clean drop-in:

- `npm ci` cannot run because there is no lockfile.
- A fresh `npm install` resolved TypeScript 7 and broke the Hardhat/ts-node path.
- Pinning TypeScript 5.7.3 allowed all 21 Solidity files to compile, but the suite finished with 0 passing and 4 failing tests: three stale constructor calls and a missing `DistributionMathHarness` artifact.
- `SECURITY.md` says audited while `docs/security.md` says unaudited; no report was available to establish scope or commit.
- The keeper address in the deployment JSON contains only 39 hexadecimal characters and is not a valid EVM address.
- The documented old index address has no deployed bytecode.
- `amountOutMinimum=0` is present in the swap flow.

This does not make the accumulator idea useless. It means we should extract the mathematical design, rewrite it for a bounded multi-asset controller using current OpenZeppelin code, and build a new invariant-tested system rather than “fork and ship.”

## Adapter compatibility experiments

These are the next transactions worth paying for. They are deliberately tiny and should use a dedicated test wallet.

### Bags spike

1. Deploy a minimal receiver with no privileged withdrawal except to the reward controller.
2. Create a low-value launch assigning a small creator share to the receiver.
3. Generate a small buy and sell through the official flow.
4. Prove the receiver's share appears in canonical onchain accounting.
5. Claim through the receiver and verify exact assets, amounts and events.
6. Change no configuration if the fee-share representation is intended to be immutable; otherwise document the controlling authority.
7. Repeat against a mainnet fork with an implementation-upgrade simulation.

Pass means the complete path works without an EOA signature assumption, manual platform intervention, or an unrestricted external call. Fail means use pons or proceed native.

### pons spike

Repeat the same experiment with the receiver as `feeWallet`. Confirm whether fees arrive directly or require a callable claim/redirect function, whether both launch-token and WETH fees accrue, and whether any creator-only signature or UI backend is required.

### Stock execution spike

Acquire authenticated 0x and 1inch Business access. For NVDA, SPY, AAPL, TSLA and one thin asset, collect firm quotes for $100, $1,000 and $10,000 notional during open and closed underlying-market hours. Record output, fees, route, expiry, allowance target and transaction target. Reject any calldata whose input/output token, receiver, spender or target is outside an explicit allowlist.

Anonymous calls made during this research returned HTTP 401 from both providers, so documentation-level support is not enough to claim executable liquidity.

## Immediate build decision

Do not fork Vladdy, point production at the old Alloy deployment, or build the whole launchpad yet. Build two narrow proofs:

1. A three-asset native reward-accounting harness with mock issuer pause/block/burn behavior.
2. A Bags contract-recipient adapter spike, followed by pons only if Bags fails or its economics are unacceptable.

Choose the adapter MVP only if the launchpad integration is permissionless, mechanically claimable and stable enough to survive implementation upgrades. Otherwise use the native accumulator and launch stack.
